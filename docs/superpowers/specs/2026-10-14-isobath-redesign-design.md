# isobath redesign — design

Status: UI direction approved by the maintainer (2026-10-14) from `mockups/page-layouts.html` (home, topic page, mobile question, flashcard session; open it in a browser). Content licence: CC BY-NC-SA (see end). Plans: `docs/superpowers/plans/`, one per rollout step.

Mockup notes for the build: keep every contour ring inside its frame; draw leader lines from the depth labels to their rings; the real generator uses marching-squares on noise, not the mockup's wobbly circles; dark mode is not yet mocked.

## Goal
Turn the current question browser into a site for **any software engineer** that is evergreen, scales past 100 topics, and has an original, ownable identity. The content format (one `.md` per question) does not change.

## Decisions (settled by the maintainer)
- **Scope:** structure + UI — home, navigation, practice/flashcards, identity, mobile, per-topic data shards, prerendering.
- **Entry model:** pick a role, get an ordered cross-topic path.
- **Identity:** calm editorial + depth-strata motif. No illustration-led style.
- **Name:** isobath, shown "isobath, by Sachin Maurya"; tagline "engineering interviews, in depth". Hosted at `learn.sachinmaurya.com`; the lockup links to the portfolio. No separate domain or trademark now.
- **Mark:** five nested irregular contours; a bolder 3-line version for the favicon. A human designer redraws the final mark and customizes the wordmark.
- **Rendering:** keep the Vite app and prerender every route to static HTML, then hydrate (approach B).
- **Out of scope:** accounts, backend, new content formats, translations.

## 1. Data: per-topic shards
Today `app/public/data/` holds one index, one search index and one flashcards file (~490 KB at 197 questions; ~20× at ~4,000).
- `manifest.json` — topics, tracks, chapter list, counts, status mix, lifecycle label. Loaded on every page.
- `topics/<topic>/index.json`, `search.json`, `flashcards.json` — loaded on demand.
- ⌘K searches the manifest (titles) first; full-text shards load when a topic is opened or chosen via a scope toggle ("This topic / All").
- Generated by `scripts/build.ts` (R3). Nothing hand-written.

## 2. Brand
- Tokens: Geist, Geist Mono, Newsreader (SIL OFL); accent `#2F4FD8` light / `#9DAEF7` dark; prose column 720px. R13 is updated to match what the app really uses.
- **Topic covers** are contour maps generated from topic slug + data by a pure function (`app/src/lib/contours.ts`), so the same code runs in the browser and, later, in the prerender step: chapters = levels, difficulty mix = crowding. Chaining marching-squares segments removes stray fragments. Original by construction, zero drawing per topic.
- **Charts** use the 4-level depth scale (30-second answer · full answer · follow-ups · spec/engine) instead of generic bars. Built with the `dataviz` skill rules.
- **OG images:** moved to the prerender step (§6): resvg-js needs TTF/OTF fonts and `@fontsource` ships only woff/woff2, so the font source and rasterizer are chosen and verified there, together with per-page meta tags.
- Legal: the maintainer makes the creative choices and keeps the drafts as a record; a human designer redraws the final mark; trademark clearance only if the brand outgrows the personal name. Remind the maintainer before the logo is final.

## 3. Navigation
- Header: **Paths · Topics · Practice · Roadmap**, search (⌘K), theme toggle, lockup.
- Topic switcher: a command-style menu grouped by track; scales to 100 topics.
- Topic page: filterable chapter outline, collapsible; "On this page" rail on questions.
- **Mobile:** question first, chapter list behind a "Chapters" disclosure (fixes the buried title).
- Breadcrumbs stay.
- Header links to Paths, Practice and Roadmap are added by the steps that create those pages; the topic switcher ships first. The manifest needs no chapter lists: the switcher uses topic titles and tracks, and the outline uses the topic shard.

## 4. Home and paths
- Home: hero with tagline → "What are you preparing as?" (Frontend · Backend · Full-stack · Infra/DevOps · Any engineer) → **Start here** (one recommended first question) → **Available now** (topics with content) → **Roadmap** (planned topics: status + contribute link).
- `content/paths/<role>.yaml`: ordered list of `topic/chapter` entries with a one-line reason each. Validated by `content:check` (every entry resolves, no duplicates). The path page shows progress along the path and an effort estimate.
- Role pages work with whatever content exists; planned entries show as roadmap steps, not dead links.
- As built: entries are `<topic>` or `<topic>/<chapter>` (planned topics have no chapters, so topic only); each path may set a `start` question, and the home "Start here" uses the first path that does; effort = 5 minutes per question; `/paths`, `/paths/<role>` and `/roadmap` exist and the header links to Paths and Roadmap; topic folders can't be named `paths`, `practice`, `flashcards` or `roadmap`. Lifecycle pills wait for §7.

## 5. Practice and flashcards
- Hubs at `/practice` and `/flashcards`: pick topic/chapter, due count, streak-free (no gamification pressure).
- Session: keyboard shortcuts (reveal, rate, next), progress on the depth scale, end-of-session summary.
- Progress stays in localStorage; **JSON export/import** is the backup story. ts-fsrs stays.
- As built: one hub at `/practice` (Questions, Flashcards with due/new counts, Your progress) and a chapter picker at `/practice/:topic`; sessions take Space/Enter to reveal, 1–2 (practice) or 1–4 (flashcards) to rate, show a depth-gradient progress bar and an end summary; at most 20 new cards per session; backup format `isobath-progress` v1, import merges (union of read questions, most recent review per card) and never carries HTML.

## 6. Prerendering (approach B)
- Build step renders every route with react-router's `createStaticHandler` / `createStaticRouter` / `StaticRouterProvider` (v8.4.0 exports verified), writes static HTML, then the client hydrates.
- Browser-only state (progress, theme) renders neutral on the server and applies after hydration, so there is no hydration mismatch.
- Also generated: `sitemap.xml`, `robots.txt`, canonical `https://learn.sachinmaurya.com`, per-page title/description/OG.
- Hosting stays as in R14 (Vercel, `vercel.json`).
- As built: `npm run build` = content build, `tsc -b`, client build, SSR build of `src/entry-server.tsx`, then `scripts/prerender.ts` writes `dist/<path>.html` for home, paths, roadmap, practice hub and topic pickers, every topic, chapter and readable question (71 pages in production today, 270 with drafts), plus `sitemap.xml` and `robots.txt`. Each page's `<title>` (rendered by the page) is moved into `<head>` with description, canonical and OG/Twitter text tags. Vercel: `cleanUrls` serves the files; unknown paths and session pages rewrite to `app-shell.html` and render client-side. OG images are still deferred.

## 7. Evergreen
- Each topic README declares **Covers** (e.g. "ECMAScript 2025, Node 24") and last-reviewed date; shown on the topic page.
- **Stale badge** after 12 months without review (computed at build from `verified`).
- Generated `/changelog` from git history of `content/`.
- Lifecycle labels: Draft · Reviewed · Legacy (honest, visible).
- Perishable facts (versions, dates) are tagged in question frontmatter so a review pass can find them.

## 8. Rollout order (each step ships on its own)
1. Data shards + manifest
2. Brand (tokens, mark, covers, charts)
3. Navigation
4. Home + paths
5. Practice/flashcards
6. Prerender + SEO
7. Evergreen

The plan breaks these into small commits; each step keeps `npm run build` and `content:check` green.

## Risks
- Prerender + hydration mismatches → neutral server state, tested by building and loading with JS disabled.
- Contour generator produces ugly shapes for sparse topics → fixed-seed from slug, review all covers once, add a minimum-levels floor.
- Search quality drops when sharded → manifest-level title search always available; verify with a fixed query list.
- Rasterizer or font source unavailable/inconsistent → decided and verified in the prerender plan before OG work.

## Decision: content licence
CC BY-NC-SA 4.0 for question text (protects against resale; PR contributions stay simple), code stays MIT. Applying it (LICENSE files, README, site footer) is its own task, done with the brand step.
